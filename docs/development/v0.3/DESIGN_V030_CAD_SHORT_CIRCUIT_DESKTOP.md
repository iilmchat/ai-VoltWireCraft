## 2. Архитектурные решения

### 2.1 Изолированный конвейер разбора DXF/DWG

Файл не разбирается в процессе NestJS API. API сохраняет файл, ставит задачу
в BullMQ; воркер вызывает расчётное ядро, где `ezdxf` разбирает DXF. Для DWG
используется конвертер ODA File Converter (основной) или LibreDWG
(альтернатива) в том же изолированном окружении. Ограничения:

- максимальный размер файла — 50 МБ;
- таймаут разбора и конвертации — 30 с;
- удаление внешних ссылок (`XREF`), встроенных скриптов, макросов и
  произвольных XDATA до передачи модели (RULES § 5.5);
- результат — нормализованные слои `WallSchema` с координатами в метрах.

### 2.2 Миграция графа в СИ

`schemaVersion: 2` делает `waypointsM` расчётным представлением координат трассы:
пиксельные точки остаются только в подложке редактора. Перевод
`waypointsPx → waypointsM` выполняется один раз через `scaleMetersPerPx`
и проверяется Zod. Все длины, сечения, токи и мощности — `m`, `mm2`, `A`, `W`.

### 2.3 Нативный мост Tauri

Команды `save_project_dialog` и `open_project_dialog` работают с локальным
путём, выбранным пользователем, и сериализуют `VwcFileSchema` v2. Бизнес-логика
графа остаётся общей для веба и десктопа; различаются только адаптеры
хранения. Сеть не требуется (RULES § 5.4).

### 2.4 Расчёт КЗ остаётся в ядре

Ток `I_кз^(1)`, кратность срабатывания и селективность считает
`calc-engine` в `Decimal`. ИИ-агент может только вызвать инструмент и
процитировать результат; вычисления внутри модели запрещены (RULES § 5.1).
Правила — в `docs/domain/PUE_SHORT_CIRCUIT_V03.md`.

### 2.5 Альтернативы и почему отвергнуты

| Вариант | Почему отвергнут |
|---|---|
| Разбирать DXF в браузере | Нет изоляции по памяти и таймауту (RULES § 5.5) |
| Хранить пиксели и переводить при каждом расчёте | `KI-003`: риск потери точности и повторного перевода |
| Считать КЗ на TypeScript | Два источника истины и разные округления с ядром |
| Открывать/сохранять файл через браузерный API в Tauri | Зависимость от сети и песочницы, нарушение RULES § 5.4 |

## 3. Технические срезы

### 3.1 Срез A — миграция `ProjectGraphSchema` и API каталога

В `packages/shared` добавляется `ProjectGraphSchemaV2` (`schemaVersion: 2`):
поля `floorPlan`, `rooms`, `walls` сохраняются; `edges[].waypointsM` становится
обязательным для кабельных линий; `waypointsPx` удаляется из расчётных
контрактов; добавляется `catalogRef` для привязки к `catalog_devices`.

Мигратор при открытии `.vwc` v1:

    {
        "fromVersion": 1,
        "toVersion": 2,
        "convertedWaypoints": 42,
        "warnings": ["scaleMetersPerPx is null"],
        "backupPath": "project.vwc.v1.bak"
    }

Шаги: строгий разбор v1 → проверка `scaleMetersPerPx` → перевод координат
`x_m = x_px × scaleMetersPerPx` → назначение `panelSlot` для узлов щита →
валидация v2 → резервная копия `.vwc.v1.bak` → запись v2. При отсутствии
масштаба проект открывается в режиме «только план».

API каталога получает `GET /catalog/devices` с фильтрами `vendor`, `category`,
`article`, `isActive` и полем `priceRub`; ответ валидируется Zod на границе.
Клиент кэширует справочник с TTL и использует его в спецификации.

### 3.2 Срез B — импорт DXF/DWG

| Шаг | Компонент | Что происходит |
|---|---|---|
| 1 | NestJS API | `POST /projects/:id/import-cad`, проверка размера ≤ 50 МБ и расширения |
| 2 | PostgreSQL / BullMQ | задача `import-cad` со статусом `queued` |
| 3 | `calc-engine` | изоляция: память, таймаут 30 с, удаление XREF/скриптов/макросов |
| 4 | `ezdxf` / ODA / LibreDWG | разбор или конвертация в DXF, извлечение слоёв |
| 5 | `calc-engine` | нормализация стен в `WallSchema`, координаты в метрах |
| 6 | API | запись стен в граф проекта после Zod-валидации |

Ошибки фиксируются в задаче; пользователю показывается причина без стека
исключения. DWG-конвертер — опциональный компонент: без него доступен только
DXF с явным сообщением об ограничении.

### 3.3 Срез C — расчёт однофазного КЗ и селективность

Для петли «фаза-ноль» при $U_\phi = 230$ В:

    I_кз^(1) = U_ф / Z_петли
    Z_петли = R_ф + R_N + j(X_ф + X_N)
    R ≈ ρ · L / S  для каждой жилы, ρ = 0,0175 Ом·мм²/м (медь, 20 °C)

Проверки ядра:

- время отключения $t \le 0{,}4$ с для сети 230 В (`PUE-SC-1.7-TIME-04`);
- кратность срабатывания электромагнитного расцепителя:
  $I_{кз}^{(1)} \ge k_{min} I_n$, где B — $3 I_n$, C — $5 I_n$, D — $10 I_n$;
  верхние границы диапазонов 5/10/20 $I_n$ используются для оценки зоны
  неопределённости и проверки селективности;
- токовая/временная селективность: кривые $t(I)$ нижестоящего и вышестоящего
  аппарата не пересекаются, выдержка различается не менее чем на 0,1 с.

Ответ содержит `shortCircuitCurrentA`, `loopImpedanceOhm`, `tripTimeS`,
`multiplicity`, `selectivityOk`, `warnings` и `references`.

### 3.4 Срез D — рендер DXF, живые цены и нативные диалоги

- **Konva.js:** векторный слой DXF — линии, дуги, полилинии и тексты
  преобразуются в примитивы холста; масштабирование вместе с планом.
- **Спецификация:** цены из `GET /catalog/devices`, резерв — локальный
  справочник при недоступности API; в XLSX/CSV попадает дата прайса.
- **Tauri:** команды `save_project_dialog` и `open_project_dialog`, запись
  `VwcFileSchema` v2 на диск, индикатор офлайн-режима в шапке.

## 4. Совместимость и миграция

### 4.1 Автоматическая миграция `.vwc` v1

При открытии файла v1 выполняется мигратор из § 3.1. Исходный файл
копируется в `<имя>.vwc.v1.bak`; перезапись производится только после
успешной валидации v2. Пользователь получает отчёт с числом преобразованных
точек и предупреждениями.

### 4.2 Обратная совместимость

v0.3.0 читает `.vwc` v1 и v2; запись всегда выполняется в v2. Обратный
переход v2 → v1 не поддерживается: для передачи в старую версию требуется
экспорт с пересчётом пиксельных координат.

### 4.3 База данных

Изменения схемы ограничены добавлением `catalogRef` и полей цены в
`catalog_devices`; Drizzle-миграция применяется до старта приложения.
Миграции тестируются на PGlite (`KI-002` остаётся открытым ограничением).

### 4.4 Откат

Откат на `v0.2.0` возможен для проектов v1; проекты v2 требуют экспорта
в v1. Конвертер DWG остаётся опциональным — его отсутствие не ломает DXF.

## 7. Риски и открытые вопросы

### 7.1 Проприетарный DWG

ODA File Converter требует отдельной лицензии и не гарантирует точности
преобразования современных версий DWG. LibreDWG — открытая альтернатива
с ограниченной поддержкой. Снижение риска: конвертер опционален, basic DXF
работает без него, результат конвертации проверяется Zod и показывается
пользователю как предварительный.

### 7.2 Изоляция разбора

50 МБ и 30 с могут не покрывать сложные чертежи. Снижение риска: отдельных
процесс с квотами, тесты на враждебные файлы и очистка внешних ссылок до
разбора (RULES § 5.5).

### 7.3 Точность расчёта КЗ

Упрощённая модель петли «фаза-ноль» не учитывает все смежные inductance
и температуру жилы. Снижение риска: явная формула в протоколе, консервативное
значение ρ и проверка по граничным случаям в тестах.

### 7.4 Открытые вопросы

| Вопрос | Кому | Статус |
|---|---|---|
| Выбрать основной конвертер DWG: ODA или LibreDWG | Архитектор | Открыт |
| Уточнить минимальную выдержку селективности: 0,1 с | Архитектор | Открыт |
| Политика кэша цен: TTL и источник даты прайса | Владелец продукта | Открыт |
| Порядок подписи релизного билда Tauri | Владелец продукта | Открыт |
