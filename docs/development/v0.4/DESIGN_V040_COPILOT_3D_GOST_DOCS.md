## 1. Контекст

### 1.1 Точка старта

**Релиз:** `v0.3.0` опубликован; 200 тестов зелёные. Реализованы импорт DXF,
расчёт однофазного КЗ, граф `schemaVersion: 2`, живой каталог и нативный
десктоп Tauri.
**Продукт:** САПР электрических сетей 0,4 кВ и сборки щитов НКУ для ИЖС,
квартир и коммерческой недвижимости.
**Стек:** NestJS 12, React 19 + Vite + Konva.js + Tauri, Python/FastAPI,
PostgreSQL 17 + pgvector, Drizzle ORM, BullMQ + Redis.
**Документы:** RULES v1.0.0, `DESIGN_V030`, `PUE_RULES_V02.md`,
`PUE_SHORT_CIRCUIT_V03.md`, `fixtures/golden-dataset/README.md`.

### 1.2 Проблема

Текущие ИИ-инструменты (`PanelArchitectAgent`, `PueAuditorAgent`) решают
отдельные задачи и возвращают результат, который пользователь вручную
переносит в проект. Нет единого диалогового интерфейса, нет объёмного
представления щита и нет готового комплекта документации для сдачи.
Одновременно отсутствует эталонный набор проектов для сквозной проверки
всех трёх направлений.

### 1.3 Новые возможности

| Возможность | Обозначение | Что делает |
|---|---|---|
| ИИ-чат-копилот | `CopilotChatAgent` | Мутация графа по команде на естественном языке через `GraphPatchProposal` с предпросмотром |
| 3D-щит | `Panel3DView` | Пятая проекция графа: корпус, DIN-рейки, модули и шинки в Three.js |
| Комплект РД | `export/gost-pdf` | Многостраничный PDF по ГОСТ Р 21.101: титул, общие данные, схема, журнал, спецификация |
| Золотой датасет | `fixtures/golden-dataset/` | Три эталонных объекта для сквозного smoke-теста в Docker |

### 1.4 Продуктовые сценарии

1. Пользователь пишет «добавь мастер-выключатель» — копилот предлагает патч,
   показывает diff, после подтверждения граф меняется и доступен Undo.
2. Инженер переключается на вкладку «3D-щит» и визуально проверяет размещение
   модулей по `panelSlot` перед сборкой.
3. По кнопке «Сформировать РД» формируется PDF со штампом организации.
4. CI прогоняет золотой датасет и сравнивает показатели с контрольными.

### 1.5 Цели и критерии успеха

- Любая мутация графа проходит через `GraphPatchProposal`, Zod-валидацию и
  явное подтверждение; отмена восстанавливает предыдущее состояние (Undo/Redo).
- LLM не выполняет расчёты: все числа приходят из `calc-engine` (RULES § 5.1).
- 3D-щит и остальные проекции читают один граф (RULES § 5.2).
- PDF-комплект содержит обязательные листы и корректный штамп ГОСТ Р 21.101.
- Сквозной smoke-тест на трёх эталонных объектах проходит в Docker.

## 2. Архитектурные решения

### 2.1 Безопасная мутация графа через чат

    Команда пользователя
        ↓
    CopilotChatAgent: распознавание намерения
        ↓ вызов инструментов calc-engine (только для чисел)
    GraphPatchProposal: { ops, reason, toolCalls, citations }
        ↓ Zod-валидация + предпросмотр diff
    Подтверждение пользователя
        ↓
    Применение патча к ProjectGraph + запись в историю Undo/Redo
        ↓
    Все проекции (план, щит, схема, спецификация, 3D) обновляются из графа

Патч — декларативный список операций (`addNode`, `updateNode`, `addEdge`,
`removeEdge`, `setStampMeta`). Прямая запись в граф из LLM запрещена; без
подтверждения изменения не применяются. Каждая операция имеет обратную
операцию для Undo.

### 2.2 Пятая проекция единого графа

3D-вид щита НКУ на базе `Three.js` / `@react-three/fiber` строится из
`nodes[].panelSlot`, `catalog_devices.dinModules` и `specs`. Это проекция,
а не отдельная модель: изменение номинала в инспекторе сразу видно в 3D
(RULES § 5.2).

### 2.3 Генератор комплекта РД по ГОСТ Р 21.101

Комплект формируется из графа и опционального блока `stampMeta`
(организация, объект, шифр, стадия, лист, подписи). Структура: титульный
лист и общие данные, однолинейная схема, кабельный журнал, спецификация.
Штамп и нумерация листов ведутся централизованно, чтобы избежать
расхождений между страницами.

### 2.4 Золотой датасет как контракт качества

Три эталонных проекта описаны в `fixtures/golden-dataset/README.md`;
сквозной тест в Docker проверяет загрузку, расчёты, генерацию РД и
совпадение контрольных показателей с допуском.

### 2.5 Альтернативы и почему отвергнуты

| Вариант | Почему отвергнут |
|---|---|
| Применять ответ LLM напрямую к графу | Риск невалидной структуры и скрытых расчётов |
| Хранить 3D-сцену отдельным файлом | Нарушение Graph-First (RULES § 5.2) |
| Генерировать PDF из произвольного Markdown | Нет управляемого штампа и стабильной нумерации листов |
| Проверять только юнит-тестами | Не покрывается сквозной путь «проект → РД» |

## 3. Технические срезы

### 3.1 Срез A — золотой датасет и сквозной smoke-тест

Каталог `fixtures/golden-dataset/`:

1. `apartment-1room-230v.vwc` — однокомнатная квартира, 230 В.
2. `apartment-3room-400v.vwc` — трёхкомнатная квартира, 400 В, мастер-выключатель, мокрые зоны.
3. `house-bath-80m.vwc` — загородный дом ИЖС, трасса 80 м на баню.

Сквозной тест в Docker: поднять `docker compose`, загрузить каждый `.vwc`,
выполнить расчёты, сформировать РД, сравнить показатели с контрольными
из `README.md` датасета. Результат — артефакты PDF и JSON-отчёт.

### 3.2 Срез B — `CopilotChatAgent`

Эндпоинт `POST /projects/:id/ai/chat`, тело: `message`, `history`,
`previewOnly`. Агент:

- распознаёт намерения: «добавь мастер-выключатель», «выдели линию на
  духовой шкаф», «переведи щит на КЭАЗ»;
- вызывает инструменты `calc-engine` (`line-sizing`, `short-circuit`,
  `auto-panel`) и каталог (`GET /catalog/devices`);
- возвращает `GraphPatchProposal` с полями `ops`, `reason`, `toolCalls`,
  `citations`, `preview` (diff) и `undoOps`.

Ограничения: лимит инструментов на один запрос, запрет числовых значений
без ссылки на `toolCalls`, Zod-валидация ответа. Применение патча — отдельный
эндпоинт `POST /projects/:id/ai/chat/apply` с подтверждением.

### 3.3 Срез C — вкладка «3D-щит»

`Panel3DView` на `@react-three/fiber`: процедурная модель корпуса НКУ,
35 мм DIN-реек, модульных аппаратов (ширина по `dinModules`), шинок
L1/L2/L3/N/PE и маркировки. Подписи и цвета берутся из каталога и `specs`.
Клик по модулю выделяет соответствующий узел графа и открывает инспектор.
Поддержка вращения, масштаба и режима «вид спереди».

### 3.4 Срез D — генератор комплекта РД

`POST /projects/:id/export/gost-pdf` (или клиентский генератор) формирует
многостраничный PDF: титульный лист, «Общие данные», однолинейную схему,
кабельный журнал и спецификацию. Штамп по ГОСТ Р 21.101 заполняется из
`stampMeta`; при отсутствии данных используются значения по умолчанию
с пометкой «заполнить». Для кириллицы встраивается TTF-шрифт.

## 4. Совместимость и миграция

### 4.1 Версия графа

`schemaVersion` остаётся `2`. Добавляется опциональный блок `stampMeta`
(необязательное поле, не влияющее на расчёты). Старые `.vwc` v2 читаются без изменений;
новое поле появляется только при первом экспорте РД.

### 4.2 История Undo/Redo

Для каждого применённого патча сохраняются `undoOps` и снимок графа.
История хранится в памяти сессии; экспорт в `.vwc` не включает историю.
При закрытии проекта история очищается.

### 4.3 База данных

Новые таблицы не требуются: чат и запросы на патч пишутся в журнал аудита
существующей схемы. Штамп хранится в `graph_json` как часть `stampMeta`.

### 4.4 Откат

Откат на `v0.3.0` возможен: `stampMeta` игнорируется старой схемой, остальные
поля графа не меняются. 3D-вид и РД недоступны в старой версии.

## 6. Что НЕ входит в v0.4.0

- нативный парсинг DWG (`KI-005` остаётся отложенным);
- расчёт трёхфазного КЗ и проверка отключающей способности;
- автоматическое применение патчей без подтверждения пользователя;
- совместная работа нескольких пользователей и облачная синхронизация;
- импорт 3D-моделей производителей и сборка шкафов во внешних САПР;
- подпись сертификатами EV Code Signing;
- генерация РД в форматах, отличных от PDF.

## 7. Риски и открытые вопросы

### 7.1 Галлюцинации при мутации графа

Агент может предложить лишнюю операцию или неверный номинал. Снижение риска:
Zod-валидация патча, предпросмотр diff, подтверждение пользователя,
обязательные `toolCalls` для чисел (RULES § 5.1).

### 7.2 Производительность 3D

Большой щит с 54 модулями может тормозить. Снижение риска: инстансинг
типовых модулей, ограничение детализации, lazy-загрузка вкладки.

### 7.3 Оформление РД

Штамп и шрифты могут расходиться с требованиями ГОСТ Р 21.101.
Снижение риска: единая функция формирования штампа, встроенный TTF, тесты на
структуру и нумерацию страниц, возможность ручной правки `stampMeta`.

### 7.4 Открытые вопросы

| Вопрос | Кому | Статус |
|---|---|---|
| Утвердить состав листов РД и шаблон штампа | Владелец продукта | Открыт |
| Выбрать формат хранения истории чата в сессии | Архитектор | Открыт |
| Требуется ли серверный PDF или достаточно клиентского | Архитектор | Открыт |
| Допустимые отклонения контрольных показателей датасета | Владелец продукта | Открыт |
