# Правила разработки VoltWireCraft

**Версия:** 1.0.0
**Дата:** 2026-11-19
**Copyright:** © 2026 RuChating (iilmchat) · VoltWireCraft vX.Y.Z
**Назначение:** единый свод правил для команды и ИИ-ассистентов.

При работе над проектом **все** изменения должны соответствовать этим правилам.
Нарушение → комментарий при проверке со ссылкой на конкретный пункт.

**Стек проекта:** NestJS 12 · TypeScript (strict) · React 19 + Vite + Konva.js ·
Tauri · Python (FastAPI, расчётное ядро) · PostgreSQL 17 + pgvector · BullMQ +
Redis · Zod · Docker Compose.

## § 1. Базовые правила

| # | Правило |
|---|---|
| 1.1 | Комментарии и JSDoc — **на русском языке** |
| 1.2 | JSDoc обязателен для всех `export`-членов: `@param`, `@returns`, `@throws` |
| 1.3 | Внедрение зависимостей — **только через конструктор** |
| 1.4 | Все методы ввода-вывода — с суффиксом `Async` (`loadProjectAsync`, `parsePlanAsync`) |
| 1.5 | `public`-члены — `camelCase`, приватные поля — `#private` или `private readonly` |
| 1.6 | Контроллеры: единый формат ответа и ошибок (например, `{ success, data, message }`) |
| 1.7 | Сервисы: выбрасывать исключение, **не гасить стек** |
| 1.8 | Версия приложения — из `package.json` / `process.env.npm_package_version` |
| 1.9 | Copyright в файлах: `© 2026 RuChating (iilmchat) · VoltWireCraft vX.Y.Z` |
| 1.10 | Все найденные проблемы → `docs/KNOWN_ISSUES.md` с номером `KI-XXX` |
| 1.11 | `strict: true` в `tsconfig.json` — не отключать; `any` запрещён, `unknown` — с явным сужением |
| 1.12 | Все внешние данные (HTTP, env, JSON, файлы проекта) — валидация через **Zod на границе** |
| 1.13 | В документах использовать устоявшиеся электротехнические термины: ЭУИ, НКУ, ВРУ, УЗО, АВДТ, ПУЭ-7, УГО |

## § 2. Документация (в том же коммите, что и код)

| # | Правило |
|---|---|
| 2.1 | `CHANGELOG.md` (Keep a Changelog) — обновляется вместе с кодом, не задним числом |
| 2.2 | Секция `[Unreleased]` — рабочая; при релизе → `[X.Y.Z] — YYYY-MM-DD`, сверху — пустая `[Unreleased]` |
| 2.3 | `README.md` — обновляется при изменении API, требований и порядка установки |
| 2.4 | `docs/KNOWN_ISSUES.md` — любая найденная проблема (даже «не баг») → запись `KI-XXX` |
| 2.5 | `docs/development/vX.Y/DESIGN_*.md` — дизайн-документ для крупных фич |
| 2.6 | Секреты и учётные данные — **никогда** в git (только `.env` / `.env.example` / хранилище секретов) |
| 2.7 | После релиза — обновить версию в `package.json` и `CHANGELOG.md` |
| 2.8 | Ссылка на `KI-XXX` в сообщении коммита обязательна, если фикс связан с реестром |
| 2.9 | В текстах MD-файлов не использовать буквальные шаблоны ключей доступа; писать описательно |
| 2.10 | **Формат передачи MD-файлов через чат.** Формат A (рекомендуемый; кнопка «Копировать» работает): внешний блок — тройной бэктик с языком `markdown`, внутренние блоки кода — **4-пробельный отступ**. Формат B (только при неудобстве отступа): внешний блок — четыре бэктика, внутри — обычные тройные. Для LLM-ассистентов и людей — формат A |
| 2.11 | Большие MD-файлы (README, CHANGELOG, RULES) не выводить целиком при точечных правках — давать «Найти / Заменить на» |
| 2.12 | При закрытии `KI-XXX` — точечный diff на `CHANGELOG.md` и `KNOWN_ISSUES.md`, а не проза |
| 2.13 | DESIGN-документ крупной фичи содержит **8 обязательных секций** по § 2.14 |
| 2.14 | Структура DESIGN-документа: 1) Контекст (какие KI закрывает), 2) Ключевое архитектурное решение, 3) Технические секции по срезам, 4) Совместимость и миграция, 5) План работ (подшаги с оценками), 6) Что НЕ входит в релиз, 7) Риски и открытые вопросы, 8) Решения (заполняется после ревью). При передаче в чат — формат § 2.10-A |

**Типы записей в CHANGELOG:** `Added`, `Changed`, `Deprecated`, `Removed`,
`Fixed`, `Security`, `Documented`.

## § 3. Рабочий процесс

| # | Правило |
|---|---|
| 3.1 | Маленькие шаги: крупная фича разбивается на 3–5 подшагов |
| 3.2 | 1 шаг = 1 коммит; не смешивать несвязанные изменения |
| 3.3 | Перед коммитом — `git status --short` |
| 3.4 | `git add -A` вместо выборочного добавления |
| 3.5 | После отправки изменений — проверить задания CI |
| 3.6 | Локально: сборка без ошибок и предупреждений |
| 3.7 | Все тесты зелёные перед отправкой изменений |
| 3.8 | После каждого код-шага — сразу docs-коммит (CHANGELOG + KI) |
| 3.9 | Сводка реестра KI пересчитывается поиском по файлу, а не по памяти |
| 3.10 | Временные отладочные скрипты после задач удаляются |
| 3.11 | Не коммитить `dist/`, `node_modules/`, `.env`, `*.tsbuildinfo` |

## § 4. Технические правила

| # | Правило | Причина |
|---|---|---|
| 4.1 | ESM: относительные импорты заканчиваются на `.js` | `ERR_MODULE_NOT_FOUND` |
| 4.2 | Типовые импорты — через `import type { ... }` | Меньше граф зависимостей |
| 4.3 | Декораторы NestJS требуют `emitDecoratorMetadata` и `experimentalDecorators` | DI не работает |
| 4.4 | `reflect-metadata` — первой строкой в точке входа | DI не работает |
| 4.5 | Переменные окружения валидируются Zod при старте с немедленным отказом при ошибке | — |
| 4.6 | Конфигурация читается через `ConfigService`, а не напрямую из окружения | Типизация и тесты |
| 4.7 | Глобальный фильтр исключений и глобальный `ValidationPipe` с `whitelist` | Единый контракт ошибок |
| 4.8 | Отдельные задачи (разбор подложек, расчёты) — в BullMQ, а не в HTTP-запросе | Долгие операции |
| 4.9 | Граф проекта хранится в `jsonb` с `$type<ProjectGraph>()` | Типизация |
| 4.10 | FK + CASCADE обязательны для связанных таблиц | Целостность данных |
| 4.11 | Идентификаторы сущностей графа — UUID (`gen_random_uuid()`) | Стабильность ссылок |
| 4.12 | `onModuleDestroy` / `OnApplicationShutdown` закрывают пулы и очереди | Процесс не зависает |
| 4.13 | `Promise.allSettled` для независимых операций; не `await` в цикле | Отказ одного шага не роняет остальные |
| 4.14 | Внешние вызовы (HTTP, БД, ядро, файлы) — в `try / catch` с таймаутом | — |
| 4.15 | `AbortController` для длительных операций | — |
| 4.16 | Snake_case в БД, camelCase в TypeScript | — |
| 4.17 | Опциональные поля графа не кодируют единицу измерения в имени | § 5.3 |
| 4.18 | Konva.js: геометрия узлов и связей выводится из графа, а не хранится в состоянии интерфейса | Graph-First (§ 5.2) |
| 4.19 | Разбор PDF/DXF/DWG — только в изолированном процессе расчётного ядра | § 5.5 |

## § 5. Доменные правила VoltWireCraft

| # | Правило |
|---|---|
| 5.1 | **Разделение ИИ и математики.** LLM-агентам строго запрещено вычислять сечения кабелей, токи короткого замыкания и номиналы аппаратов защиты. Расчёты выполняются **только** вызовом инструментов детерминированного расчётного ядра `calc-engine` (Python/FastAPI). Агент может интерпретировать результат, но не подменять его |
| 5.2 | **Graph-First.** План этажа (Konva.js) и однолинейная схема — проекции единого JSON-графа проекта (`ProjectGraphSchema`). Источник истины — граф; любая правка вносится в него, представление перерисовывается из графа. Расхождение между проекциями — дефект |
| 5.3 | **Единицы измерения (СИ).** Все физические величины в базе данных, графе и API хранятся строго в базовых единицах: `m`, `W`, `V`, `A`, `mm2`. Перевод в другие единицы — только на слое отображения; в имени поля единица не кодируется |
| 5.4 | **Офлайн-режим Desktop.** Настольное приложение (Tauri) обязано поддерживать локальное сохранение и открытие файлов проекта (`.vwc` / JSON) без доступа к сети. Любая новая функция, требующая сервер, обязана иметь офлайн-поведение или явное сообщение о недоступности |
| 5.5 | **Сандбоксинг CAD-файлов.** Разбор пользовательских PDF/DXF/DWG выполняется в изоляции с ограничениями по памяти и времени (таймауту). Внешние ссылки, встроенные скрипты и макросы не исполняются; результат разбора валидируется Zod |
| 5.6 | **Электротехническая терминология.** В документации и интерфейсе применяются устоявшиеся термины: ЭУИ, НКУ, ВРУ, УЗО, АВДТ, ПУЭ-7, УГО. Не допускается замена их разговорными или машинными переводами |

## § 6. Безопасность

| # | Правило |
|---|---|
| 6.1 | Секреты — только в `.env` (разработка) или хранилище секретов (прод) |
| 6.2 | `.env` в `.gitignore`; `.env.example` — с заглушками |
| 6.3 | Пароли в строках подключения не логируются |
| 6.4 | Пользовательские файлы не попадают в логи целиком; логируется хэш и размер |
| 6.5 | Загрузки проходят проверку типа, размера и ограничений из § 5.5 |
| 6.6 | Перед релизом — поиск утечек в истории коммитов |

## § 9. Как использовать

**При работе над задачей:**

1. Открыть этот файл и вспомнить применимые правила, особенно § 5.
2. Мелкими шагами коммитить каждый шаг.
3. В том же коммите обновить `CHANGELOG.md`, а при необходимости — `README.md` и `KNOWN_ISSUES.md`.
4. Проверить сборку и тесты локально.
5. Отправить изменения, проверить CI.

**При ревью:**

1. Проверить § 1–2 (базовые правила и документация).
2. Технические замечания — по § 4, доменные — по § 5.
3. Ссылаться на конкретный пункт, например: «нарушение 5.1 — расчёт сделан в агенте».

**При знакомстве с проектом:**

1. Прочитать файл целиком.
2. Прочитать `docs/KNOWN_ISSUES.md`.
3. Прочитать `docs/CHANGELOG.md` (последний релиз).
4. Настроить окружение, запустить сервисы и тесты.
