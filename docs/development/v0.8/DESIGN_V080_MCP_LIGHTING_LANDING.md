## 1. Контекст

### 1.1 Точка старта

**Релиз:** `v0.7.0` опубликован; 279 тестов зелёные. Реализованы подписанное
автообновление Tauri и темы Material 3 по брендбуку `ai-brand`.
**Продукт:** САПР электрических сетей 0,4 кВ и сборки щитов НКУ для ИЖС,
квартир и коммерческой недвижимости.
**Стек:** NestJS 12, React 19 + Vite + Konva.js + Tauri 2, Three.js,
Python/FastAPI, PostgreSQL 17 + pgvector, MCP-серверы.
**Документы:** RULES v1.0.0, `DESIGN_V070`, `LIGHTING_SP52_V08.md`.

### 1.2 Проблема

Проектировщик щита НКУ сегодня вручную переносит спецификацию в складской
учёт и CRM, а базовый светотехнический расчёт выполняется вне системы.
Кроме того, у продукта нет публичной витрины: потенциальный пользователь
не может ознакомиться с возможностями и скачать десктоп без клонирования
репозитория.

### 1.3 Новые возможности

| Возможность | Обозначение | Что делает |
|---|---|---|
| Склад и CRM | `moysklad-mcp`, `bitrix24-mcp` | Проверка остатков, создание заказов и сделок через MCP с подтверждением |
| Светотехника | `POST /v1/calc/lighting` | Расчёт освещённости по СП 52.13330 методом коэффициента использования |
| Копилот | `calculate_room_lighting_tool` | Вызов расчёта по вершинам зоны `RoomZone` без вычислений в LLM |
| Лендинг | `/` и `/editor` | Публичная витрина, вход в редактор и ссылки на десктоп |
| Документация | `USER_GUIDE.md` | Руководство пользователя в фирменном стиле |

### 1.4 Продуктовые сценарии

1. Сборщик щита проверяет остатки автоматических выключателей в МойСклад
   перед сборкой; при нехватке копилот предлагает заказ, который создаётся
   только после явного подтверждения.
2. Инженер выбирает комнату на плане — инспектор показывает нормативную
   освещённость, число светильников и индекс помещения.
3. Смета отправляется в сделку Битрикс24 кнопкой «Отправить спецификацию».
4. Пользователь открывает сайт продукта, нажимает «Открыть редактор»
   или скачивает десктоп для Windows/Linux; в Tauri сразу открывается
   редактор без лишнего экрана.

### 1.5 Цели и критерии успеха

- Все записи во внешние системы проходят через HITL-подтверждение.
- Токены интеграций не попадают в git и не хранятся в открытом виде (RULES § 6).
- Светотехнический расчёт детерминирован и покрыт тестами на эталонные зоны.
- Лендинг и руководство доступны без авторизации; в Tauri нет лишнего экрана.
- Тесты, сборка, линтер и типы зелёные.

### 1.6 Что не является целью

Перечень приведён в § 6.

## 2. Архитектурные решения

### 2.1 MCP-обёртки с HITL

Интеграции реализованы как MCP-серверы в `infra/mcp/moysklad/` и
`infra/mcp/bitrix24/` по стандарту архитектуры `SkillWharf`. Каждый сервер
предоставляет инструменты чтения (`get_stock`, `find_deal`) и записи
(`create_order`, `create_deal`, `send_estimate`). Инструменты записи требуют
`confirmationToken`: агент показывает пользователю параметры операции,
и только после подтверждения вызывает MCP. Токены хранятся в.env или
зашифрованным в хранилище секретов, никогда не логируются.

### 2.2 Светотехнический расчёт в ядре

Площадь зоны по вершинам полигона `RoomZone` считается по формуле
шнурования (Гаусса). Индекс помещения $i = S / (h_p (a + b))$,
коэффициент использования $\eta$ берётся из `LIGHTING_SP52_V08.md`.
Требуемый световой поток:

    Φ = E_н · S · K_зап / η

где $K_зап$ — коэффициент запаса. Число светильников
$N = \lceil \Phi / \Phi_{св} \rceil$. Все расчёты — в `Decimal`, внутри
`calc-engine` (RULES § 5.1).

### 2.3 Роутинг фронтенда

В Web корневой путь `/` отдаёт публичный лендинг с кнопками «Открыть
редактор» → `/editor` и «Скачать Desktop (Windows/Linux)». В Tauri
`isTauri()` при старте сразу перенаправляет на `/editor`. Маршруты
используют один SPA-бандл и общие темы Material 3.

### 2.4 Альтернативы и почему отвергнуты

| Вариант | Почему отвергнут |
|---|---|
| Прямые HTTP-вызовы к CRM из UI | Утечка токенов в браузере и нет HITL |
| Автоматическое создание заказов без подтверждения | Риск нежелательных операций |
| Считать освещённость в LLM | Запрещено RULES § 5.1 |
| Отдельный статический сайт лендинга | Дублирование стилей и темы |

## 3. Технические срезы

### 3.1 Срез A — MCP-серверы и настройки интеграций

`infra/mcp/moysklad/` и `infra/mcp/bitrix24/`: конфигурация через переменные
окружения, реестр инструментов, Zod-валидация аргументов и ответов.
В `apps/api` добавляется `IntegrationsController`: список подключений,
статус, тестовый вызов и удаление токена. Запись в лог — только хэш
токена и идентификатор операции.

### 3.2 Срез B — светотехника

`POST /v1/calc/lighting` принимает `polygonM`, `ceilingHeightM`, `roomType`,
`lumenPerFixture`, `safetyFactor`; возвращает `areaM2`, `roomIndex`,
`utilizationFactor`, `requiredLumens`, `fixtureCount`, `references`.
Инструмент `calculate_room_lighting_tool` доступен `CopilotChatAgent`
и не содержит арифметики внутри модели.

### 3.3 Срез C — UI интеграций и светотехники

Карточки «МойСклад» и «Битрикс24» в настройках проекта с индикатором
подключения. В спецификации — кнопка «Отправить спецификацию в МойСклад/
Битрикс24» с диалогом подтверждения. В `InspectorPanel` комнаты — блок
светотехники: площадь, индекс помещения, норма и число светильников.

### 3.4 Срез D — лендинг и руководство

Публичная страница `/` в стиле Material 3 (`ai-brand`): ценность продукта,
сценарии, скриншоты, кнопки «Открыть редактор» и «Скачать Desktop».
`docs/user_guide/USER_GUIDE.md` — первая версия руководства с описанием
workspace, инструментов и горячих клавиш.

## 4. Совместимость и миграция

### 4.1 Версия графа

`schemaVersion` остаётся `2`. Интеграции и светотехника не меняют структуру
`ProjectGraph`; результаты расчёта хранятся в `meta` зоны как необязательные
поля. Старые проекты читаются без миграции.

### 4.2 Токены и безопасность

Существующие `.env` не требуют изменений при отсутствии интеграций.
При включении MCP добавляются новые переменные; значения не коммитятся.
Удаление подключения очищает токен в хранилище.

### 4.3 Откат

Откат на `v0.7.0` возможен: новые маршруты и блоки UI игнорируются,
проекты остаются совместимыми. Внешние операции HITL не отменяются.

## 7. Риски и открытые вопросы

### 7.1 Утечка токенов

Токены CRM и склада не должны попадать в логи, `.vwc` или frontend-бандл.
Снижение риска: хранение в.env/секрет-менеджере, маскирование в логах,
тест на отсутствие секретов в сборке.

### 7.2 Офлайн-режим Tauri

Вне сети MCP-интеграции недоступны. Снижение риска: явный статус
«офлайн», кэш последних остатков только для чтения, все записи требуют
сети и подтверждения (RULES § 5.4).

### 7.3 Точность нормативов

Значения освещённости и $\eta$ могут отличаться от действующей редакции
СП 52.13330. Снижение риска: версионирование справочника, ссылки на строки
в протоколе и предупреждение о приблизительном характере результата.

### 7.4 Открытые вопросы

| Вопрос | Статус |
|---|---|
| Хранить токены в env или зашифрованным в БД | Решён: env в dev, secret manager в prod (§ 8) |
| Показывать остатки при офлайн-работе | Решён: только кэш для чтения (§ 8) |
| Язык лендинга | Решён: русский (§ 8) |
